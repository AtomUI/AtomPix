## 1. 产品目标

AtomPix 第一阶段目标是交付一款可实际使用的跨平台桌面图片工具，核心围绕：

- 本地图片浏览与预览。
- 图片压缩。
- 图片格式转换。
- 图片尺寸调整。
- 图片裁剪。
- 压缩、转换、调整尺寸三类操作的批量处理；裁剪仅支持单张。

第一阶段不追求成为完整图片编辑器，也不追求覆盖所有专业图像格式。产品重点是把主流图片的单张压缩、转换、调整尺寸、裁剪，以及压缩、转换、调整尺寸批量处理做稳定、清晰、易用。

## 2. 第一阶段功能范围

第一阶段 MVP 包含以下能力：

```text
1. 打开图片或文件夹并预览
2. 单张图片压缩
3. 单张格式转换
4. 单张图片调整尺寸
5. 单张图片裁剪
6. 压缩、转换、调整尺寸的批量处理
7. 输出目录和覆盖策略
8. 处理前后尺寸与文件大小统计
9. 基础设置
```

### 2.1 图片处理资源保护

第一阶段为单张和批量图片处理统一设置以下硬边界：

| 项目 | 第一阶段上限 |
| --- | ---: |
| 输入文件体积 | `512 MiB`（`536870912` bytes） |
| 输入图片单边 | `32768 px` |
| 输入图片总像素数 | `128000000 px` |
| 输出图片单边 | `32768 px` |
| 输出图片总像素数 | `128000000 px` |
| 单次处理帧数 | `1` |

- 文件体积不能代替解码尺寸检查；图片必须先通过轻量头信息探测，再允许完整解码。
- 宽高乘法使用受检查的 `long` 运算，不能因整数溢出绕过像素数限制。
- 超过边界时明确拒绝当前图片，不能偷偷缩小、裁剪或降低质量继续处理。
- 这些数值是第一阶段引擎能力，不作为用户偏好，不进入设置页面或 `AppSettings`。
- Resize 的目标尺寸同时受输出边界约束；Crop、压缩和转换的输入仍受公共输入边界约束。
- 单张图片在任务接受前确认超限时返回可解释的启动拒绝，不创建 Job。
- 已接受批量任务中的某项超限或触发图片缓存资源上限时，该项失败并继续下一项；输出卷或公共临时缓存磁盘空间不足时中止批次，保留已有成功结果，剩余项目不启动。
- 资源上限只在实际处理时按需使用。应用启动时不会预留 `512 MiB` 内存、映射 `1 GiB` 空间或创建 `4 GiB` 临时文件。

## 3. 图片浏览与预览

第一阶段支持：

- 打开单张图片。
- 打开本地文件夹。
- 展示缩略图列表。
- 上一张 / 下一张切换。
- 显示图片基本信息：格式、尺寸、文件大小、路径。
- 适应窗口显示。
- 原始大小显示。
- 放大和缩小。
- EXIF 方向自动校正。
- 拖拽图片或文件夹进入窗口。
- 最近打开记录。

### 3.1 浏览器与单张快捷操作

首页的“打开图片”和“打开文件夹”都进入图片浏览器：

- 打开图片时，浏览器只载入该图片并把它设为当前图片。
- 浏览文件夹时，浏览器展示文件夹图片列表，并把列表中的一个项目设为当前图片。
- 文件夹图片列表只是浏览集合，不是批量输入列表，也不创建 `BatchJob`。
- 浏览器预览区底部提供压缩、转换、调整尺寸、裁剪四项快捷操作；四项操作都只作用于当前图片。
- 用户切换上一张、下一张或点击其他缩略图后，快捷操作的目标随当前图片改变。
- 点击快捷操作只进入对应的单张功能页，并携带当前图片路径；不得把整个文件夹或其他缩略图隐式加入任务。
- 批量处理必须从“批量任务”入口显式添加文件或文件夹后开始。
- 没有当前图片时禁用四项快捷操作。
- 用户触发单张处理后，即使浏览器当前图片随后发生切换，已经创建的请求仍使用触发时捕获的图片路径。

“打开文件夹”的第一阶段规则固定如下：

- 只枚举所选目录当前层级，不递归子目录，也不提供递归开关。
- 根据图片引擎声明的输入格式能力发现候选文件；扩展名过滤只表示“可能受支持”，不代替真实图片探测。
- 候选图片按文件名自然顺序稳定排列，例如 `image2.png` 位于 `image10.png` 之前；同名比较结果相同时使用规范化完整路径作为稳定决胜条件。
- 建立浏览集合时不一次性解码全部图片，也不一次性生成全部缩略图。当前图片优先加载，缩略图按可见区域延迟加载。
- 当前图片默认先生成适合窗口浏览的轻量主预览；用户选择“原始大小 / 1:1”时，才按原图像素边界请求完整尺寸预览。该请求仍受公共文件、宽高、像素数和缓存资源上限约束，失败时保留已有轻量预览并显示可恢复错误。
- 首个候选项加载失败时保留为错误占位并继续尝试下一项，直到找到首个可用图片；后续损坏、伪装格式或已经删除的项目同样保留为不可用项，允许用户从浏览集合移除。
- 目录存在且可访问、但没有受支持图片时，打开操作仍然成功，进入图片浏览器空态。
- 目录不存在或不可访问时停留在首页并显示可恢复错误；用户取消选择或加载不显示严重错误。
- 浏览期间不监听目录新增、删除或重命名。磁盘内容变化只在项目再次加载时反映；需要完整刷新时返回首页重新打开目录。
- 第一阶段只使用当前浏览会话内的预览缓存，不建立持久化磁盘缩略图缓存。

第一阶段暂缓：

- 完整相册管理。
- 标签、收藏、评分。
- 图片搜索。
- 云端图片浏览。
- 多设备同步。

## 4. 图片格式转换

第一阶段支持输入格式：

```text
JPEG / JPG
PNG
WebP
BMP
GIF
TIFF
```

第一阶段支持输出格式：

```text
JPEG / JPG
PNG
WebP
```

第一阶段支持：

- 单张转换。
- 批量转换。
- 输出目录选择。
- 覆盖策略：跳过、覆盖、自动重命名。
- 转换前后文件大小对比。
- 转换失败原因列表。

转换表示把输出统一编码为用户选择的目标格式。批量转换共享一个目标格式；如果某个输入原本已经是该格式，仍按当前质量、元数据和透明度策略重新编码，不把它记为 Skipped，也不静默复制源文件。

透明区域处理属于转换结果的一部分，第一阶段采用确定性规则：

- 图片探测区分“包含 Alpha 通道”和“真实存在透明像素”；转换业务、页面提示和批量统计只使用后者。
- 目标 PNG / WebP 支持透明度时保留透明像素，不提供主动铺底去透明选项。
- 目标 JPEG 不支持透明度；源图真实存在透明像素时，必须先按用户指定的不透明 sRGB 背景色合成，再编码为 JPEG，不能依赖图片引擎默认背景。
- 默认背景色为白色 `#FFFFFF`。设置页保存默认值；单张和批量转换页可以为当前任务覆盖。
- 单张请求冻结当次背景色；批量转换中的所有项目共享同一个背景色并冻结为运行快照。无透明像素的项目忽略该参数。
- 转换结果明确报告透明度未出现、已保留或已铺底；铺底结果同时报告实际背景色。

所有单张和批量处理共享以下源文件保护规则：

- AtomPix 第一阶段不允许处理结果原地覆盖任何输入图片；`Overwrite` 只允许覆盖与本次任务输入集合无关的已有目标文件。
- 单张任务使用 `Overwrite` 且计划输出路径等于输入路径时，在任务启动前阻断并弹窗提醒。
- 批量任务使用 `Overwrite` 且任一计划输出路径命中批次中的任意输入路径时，在创建批量任务前整体阻断；不得先处理安全项。
- `AutoRename` 遇到输入路径时按已有文件处理并选择新名称；`Skip` 则形成正常的 Skipped 结果。
- 弹窗只提供“改为自动重命名”和“返回修改”，不提供继续覆盖源文件的入口；改为自动重命名后仍需用户再次点击开始。
- 路径比较使用规范化绝对路径和当前平台大小写规则。第一阶段不承诺处理符号链接、硬链接、外部程序或多个 AtomPix 进程同时抢占输出路径的极端情况。

第一阶段暂缓：

- PDF / EPS / PS。
- 视频帧提取。
- PSD / AI 等设计源文件格式。
- HEIC / AVIF，后续单独评估。

## 5. 图片压缩

第一阶段支持：

- JPEG 质量压缩。
- WebP 质量压缩。
- PNG 同格式无损优化；转为 WebP 属于“转换”功能，不属于压缩。
- 保留或移除拍摄信息、位置数据和描述性元数据；ICC 色彩配置独立保留。
- 单张压缩。
- 批量压缩。
- 压缩前后大小及体积变化对比。
- 减少、不变或增加的方向化比例统计。
- 压缩结果列表。

第一阶段压缩模式：

```text
智能压缩
高质量
平衡
极限压缩
自定义
```

这些模式在实现上对应不同的质量或编码强度，不隐式改变图片格式或像素尺寸。拍摄/描述性信息由独立的 `MetadataPolicy` 控制；内置模式可以提供初始默认值，但用户的明确选择优先，ICC 色彩配置始终独立保留。

自定义压缩模式的产品规则固定如下：

- 用户选择“自定义”后，使用滑块和整数输入框编辑同一个质量值，合法范围为 `1..100`；两者双向同步。
- 空值、非整数或越界值使当前草稿无效，并禁用“开始压缩”或“开始任务”。
- 单张压缩只把自定义质量应用于当前图片；批量压缩对批次中的所有有损输出使用同一个共享质量值，第一阶段不提供逐项覆盖。
- JPEG、WebP 等有损输出使用该质量值；PNG、BMP 等无损输出不使用质量值。单张当前格式无损时隐藏或禁用质量控件；批量输入全部为无损格式时禁用并说明原因，混合批次则说明质量只影响其中的有损项目。
- 设置页允许把 `Custom + Quality` 作为完整的默认压缩配置保存。任务提交后使用不可变快照，不受页面草稿或设置的后续修改影响。
- 页面在当前会话内切换到其他模式时保留最近一次合法的自定义质量，但只有重新选择“自定义”才会把该值提交给 Workflow。

智能压缩与自定义压缩的边界：

- 用户可以选择智能压缩，但不能修改它的初始质量、递减步长、质量下限、重试次数或候选选择规则；需要指定质量时应选择自定义模式。
- Smart 对 JPEG 依次尝试 `82 -> 77 -> 72 -> 67 -> 65`，对 WebP 依次尝试 `80 -> 75 -> 70 -> 65`。第一个小于原图的候选即为结果，以优先保留最高可行画质；如果所有候选都未变小，则保存其中体积最小的有效候选。
- PNG 等无损格式不做质量递减，只使用格式支持的无损编码优化；不得为了压缩结果擅自改变输出格式。
- 压缩成功结果展示实际采用的质量；无损输出显示“无损优化”，不伪造质量值。
- 所有模式只要编码和写出成功就必须保存结果，即使输出与原图相同或更大；AtomPix 不提供“仅保留更小结果”选项，也不把体积增加判定为失败或跳过。

四类图片处理统一使用中性的文件体积变化语义。单项和批量结果按实际字节数显示“减少”“未变化”或“增加”，不得显示“节省 -N KB”。批量体积统计只比较已经成功且同时具有输入、输出大小的项目；失败、取消、跳过和未开始项不能形成虚假节省。

第一阶段压缩与转换页面只显示原图预览，不根据当前参数生成处理后效果预览，也不在正式处理前估算输出文件体积。任务成功后使用实际输入、输出字节数展示体积变化。Resize 的预计输出宽高和 Crop 的选区摘要是确定性参数计算，不属于该延期范围。

第一阶段不提供用户命名压缩预设。Smart、高质量、平衡、极限和 Custom 是内置模式；设置页仍可保存唯一的默认 `CompressionProfile`。命名预设的保存、同名覆盖、重命名、删除和独立持久化留待后续优化版本。

## 6. 调整尺寸（Resize）与裁剪边界

第一阶段必须支持 Resize。Resize 只改变输出图片的 width 和 height，不裁剪图片内容，也不自动增加留白。

Resize 分为两种方式：

### 6.1 按 Pixel Resize

- 提供 `Width` 和 `Height` 两个正整数输入框。
- 提供“保持比例”选项。
- 未勾选“保持比例”时，`Width` 和 `Height` 都必须填写；输出严格使用用户输入的宽高，允许图片产生拉伸或压缩变形。
- 勾选“保持比例”时，可以只填写 `Width` 或只填写 `Height`，另一边根据原图宽高比自动计算。
- 勾选“保持比例”且同时填写 `Width` 和 `Height` 时，将二者视为最大边界，使用两个缩放比例中的较小值计算输出尺寸，保证输出完整落在边界内。
- 保持比例计算只做等比缩放，不裁剪，也不补边。

例如原图为 `2400 × 1600`：

```text
保持比例，Width = 1200                  -> 1200 × 800
保持比例，Height = 600                  -> 900 × 600
保持比例，Width = 1200，Height = 600    -> 900 × 600
不保持比例，Width = 1200，Height = 600  -> 1200 × 600
```

### 6.2 按百分比 Resize

- 提供 `25%`、`50%`、`75%` 三个快捷选项。
- 同时提供自定义百分比十进制正数输入框，允许小数和大于 `100%` 的放大。
- 百分比同时作用于 width 和 height，因此始终保持原图比例。
- UI 应根据原始尺寸实时显示预计输出尺寸。

Pixel 和百分比 Resize 作为独立“调整尺寸”功能使用，并支持对应的批量任务。压缩和转换页可以在结果完成后提供“继续调整尺寸”的跨功能入口，但不把 Resize 参数混入压缩或转换的主设置。

Resize 输出始终保持输入图片格式，不属于格式转换：

- Resize 会重新编码整张图片，但不裁剪、不补边。
- 第一阶段原格式 Resize/Crop 范围为 JPEG、PNG、BMP 和单帧 WebP；GIF、多帧 WebP 与 TIFF 的同格式处理后续再评估。
- JPEG、WebP 等有损格式使用公共的同格式编码质量，MVP 产品值固定为 `90`；Resize/Crop 页面和设置页都不提供单独质量编辑控件。
- PNG、BMP 等无损格式忽略质量值。
- 元数据使用公共默认策略，初始默认移除；用户在设置页修改后，提交任务时把当前策略快照写入请求。
- 多帧或动画图片第一阶段拒绝 Resize。
- 任务开始后使用请求快照，即使用户随后修改设置，也不能改变正在运行任务的编码策略。

### 6.3 裁剪图片

裁剪与 Resize 是两个独立功能。裁剪只保留原图中的指定矩形区域，不拉伸内容，也不自动执行 Resize。

单张裁剪支持：

- 在预览图上拖动裁剪框改变位置。
- 拖动裁剪框的边和角改变大小。
- 输入裁剪区域 `Width` 和 `Height`，单位为 pixel。
- 输入裁剪区域左上角 `Position X` 和 `Position Y`，单位为 pixel。
- 可视裁剪框与四个数值输入实时双向同步。
- 自由比例，以及 `3:2`、`4:3`、`5:4`、`1:1`、`4:5`、`3:4`、`2:3` 常用比例。
- 一键重置为完整图片区域。
- 实时显示原图尺寸、裁剪输出尺寸和区域坐标。
- 裁剪区域不能超出图片边界，width 和 height 必须大于 0。

裁剪第一阶段只支持单张。批量裁剪不进入 MVP，也不在批量任务页显示入口；此前讨论的统一比例、最大居中选区和逐项调整方案仅作为后续备忘，不形成当前 Workflow、Feature 或验收要求。

裁剪结果保持输入图片格式，并使用统一 `OutputPolicy` 决定输出位置、文件命名和同名处理。第一阶段只处理 JPEG、PNG、BMP 和单帧 WebP；GIF、多帧 WebP 与 TIFF 暂不进入 Resize/Crop 范围。

单张裁剪提交的是自动方向校正后原图逻辑坐标系中的最终 `CropRectangle`，不再携带比例或 UI 选框状态。成功输出的 width 和 height 必须严格等于该矩形的 width 和 height；失败、取消或跳过仍保留原计划矩形用于结果解释。

裁剪完成后可以提供“继续调整尺寸”快捷入口，但两个操作保持独立任务和独立参数。

第一阶段暂缓：

- 画笔。
- 文字标注。
- 水印。
- 滤镜。
- 图层。
- 复杂图片编辑器能力。

## 7. 批量任务

第一阶段支持：

- 批量压缩。
- 批量转换。
- 批量调整尺寸。
- 批量添加文件。
- 批量添加文件夹。
- 单个前台批次的项目调度列表；第一阶段不提供可并行排队的多任务队列。
- 单项状态：等待、处理中、成功、失败、跳过、取消。
- 按已终态项目数计算的总进度。
- 单项状态与不确定“处理中”反馈；第一阶段不伪造单张图片内部百分比。
- 失败原因展示。
- 失败重试。
- 取消任务。
- 处理完成后打开输出目录。

### 7.1 批量输入收集规则

批量任务中的“添加文件”和“添加文件夹”都采用追加语义，不替换当前列表：

- “添加文件”允许在系统文件选择器中一次多选图片。
- “添加文件夹”把所选文件夹当前层级中的受支持图片追加到列表；第一阶段默认不递归子文件夹。
- 用户可以反复使用两个入口，把不同文件夹、磁盘或来源的图片组合到同一个批量作业中。
- 每次新增内容追加到当前列表末尾，不改变已有项目的顺序。
- 文件选择器返回的文件保持返回顺序；文件夹内容按相对路径稳定排序后追加，保证相同输入得到相同处理顺序。
- 使用规范化后的绝对路径去重；同一文件无论通过文件选择器还是文件夹扫描加入，都只保留一个列表项。
- 不支持的格式、重复路径、扫描时已经不存在或不可读取的文件不进入任务列表，并按原因计数。
- 每次添加完成后反馈“新增 N 项、跳过 M 个重复项、K 个不支持项、L 个不可读取项”；全部被跳过时保留原列表并说明原因。
- 用户从列表移除项目只改变当前批量作业，不删除、移动或修改磁盘上的源文件；移除后允许再次添加。
- 列表为空时不能开始批量处理。

首页“打开文件夹”只打开图片浏览体验，不创建批量作业；只有批量任务页的“添加文件夹”采用上述追加语义。

### 7.2 批量文件名格式与序号

批量任务中，一旦冻结的待处理图片数量大于 1，每项输出文件名默认携带稳定序号后缀。默认格式为：

```text
{name}_atompix_{index}
```

第一阶段提供两个占位符：

- `{name}`：原始文件名主体，不含扩展名。
- `{index}`：冻结批次中的一基序号，至少三位补零，例如 `001`。

用户可以编辑“文件名格式”，并通过“原文件名 `{name}`”“序号 `{index}`”快捷项把占位符插入光标位置。扩展名由任务类型和目标格式决定，不在格式中编辑。

规则：

- 批量数量大于 1 且用户格式没有 `{index}` 时，AtomPix 在实际格式末尾自动追加 `_{index}`；UI 必须同时显示提醒和实际生效格式。
- 用户输入纯文本 `holiday` 时，实际格式为 `holiday_{index}`，输出 `holiday_001.webp`、`holiday_002.webp`。
- 用户显式指定 `{index}` 位置时严格尊重，例如 `web_{index}_{name}`。
- 批量数量等于 1 时不自动增加序号；用户主动写入 `{index}` 时仍输出 `001`。
- 序号宽度为三位或总数量位数中的较大者；1000 项使用 `0001..1000`。
- 序号来自提交时冻结的输入顺序。失败、跳过和取消项仍占用自己的序号，后续项目不前移。
- 添加、移除输入时草稿预览可以重新编号；任务提交后，输入顺序、序号、实际格式和计划输出路径全部冻结。
- 恢复失败项或处理未完成项会建立新批量草稿，并按新草稿顺序重新编号；旧任务的文件名和输出计划保持不变。

序号用于保证本批次计划名称唯一；`Skip / Overwrite / AutoRename` 只处理计划名称与磁盘已有文件的冲突。`AutoRename` 的冲突编号位于序号之后，例如 `holiday_001_1.webp`。

### 7.3 批量 Resize 共享规则

一个 Batch Resize 使用一套共享 Resize 参数，但共享的是处理规则，不是所有项目最终解析出的像素尺寸：

- Percentage：所有图片使用相同百分比，各自根据原图尺寸计算输出尺寸。
- Pixel + 保持比例 + 单边：所有图片共享相同 Width 或 Height 约束，另一边按各自比例计算。
- Pixel + 保持比例 + 双边：Width / Height 表示共同的最大边界，每张图片分别等比适配到边界内。
- Pixel + 不保持比例：Width / Height 表示共同的确定输出尺寸，所有图片强制输出为相同尺寸，允许产生拉伸变形。

批量 Resize 默认勾选“保持比例”。勾选时，双边输入在 UI 中明确解释为“最大宽度 / 最大高度”；未勾选时 Width 和 Height 都必须填写，并显示“所有图片将强制调整为相同尺寸，部分图片可能变形”的非阻断警告。

批量列表应尽量按每张图片的原始尺寸显示预计输出尺寸；无法预探测的项目显示不可用状态，最终仍以 Workflow 执行时的 Probe 和 Core 解析结果为准。

第一阶段不提供逐项 Resize 参数覆盖。需要不同 Width / Height 或不同百分比的图片应进入单张处理或拆分成多个批次。

### 7.4 批量终态恢复与 Skipped 语义

第一阶段不恢复或重新打开已经结束的 `BatchJob`。所有恢复动作都先创建一个新的可编辑批量草稿，用户再次确认后才启动新的批量任务：

- “重试失败项”只提取旧结果中状态为 `Failed` 的输入，保持原输入相对顺序；不包含成功、跳过、取消或未开始项。
- “处理未完成项”用于用户取消或批量级中止，按原提交顺序包含 `Failed`、`Canceled` 和没有终态结果的未开始输入，排除已经 `Succeeded` 或 `Skipped` 的输入。
- “使用自动重命名处理”用于因目标已存在且覆盖策略为 `Skip` 而跳过的项目；新草稿复制原输入和处理参数，但把覆盖策略改为 `AutoRename`。
- “继续处理其他图片”仍表示建立空白新草稿，与预填旧任务输入的“处理未完成项”是两个不同动作。
- 新草稿默认复制旧任务实际提交时的任务类型、处理参数、公共编码策略和输出策略，不重新读取后来已经变化的默认设置；用户可以在新草稿中主动修改。
- 点击上述恢复动作不立即执行。用户可以先移除、重新定位输入，或修正输出目录与参数，再点击开始。
- 新任务拥有新的 BatchJobId、ImageJobId、实时进度序号和 BatchResult；旧任务及统计保持只读，新结果不合并回旧结果。

`ImageJobStatus.Skipped` 在 MVP 中只表示：目标文件已经存在，且用户提交的 `OverwritePolicy` 为 `Skip`。它是输出策略被正常执行的结果，不是错误，也不会单独把批次降级为部分成功。图片损坏、读取/写入失败或格式能力不支持属于 `Failed`；用户取消属于 `Canceled`；公共前置条件不满足属于 `StartRejected`。

批量输入收集阶段的 `BatchInputPlan.SkippedItems` 只是重复、不支持、缺失或不可读取的候选文件没有进入输入计划，不等于任务执行阶段的 `ImageJobStatus.Skipped`，因为前者从未创建 ImageJob。

### 7.5 第一阶段暂缓

- 批量裁剪。
- 暂停 / 恢复。

## 8. 基础设置

第一阶段支持：

- 默认输出目录。
- 默认覆盖策略。
- 默认文件名格式；批量多项时自动保证包含 `{index}`。
- 默认压缩模式及 Custom 质量。
- 默认转换输出格式与质量。
- 默认透明区域背景色，初始为白色 `#FFFFFF`。
- 公共默认是否移除拍摄信息与位置数据，同时写入压缩、转换和 Resize/Crop 同格式编码策略；ICC 色彩配置不受该开关控制。
- Resize/Crop 的同格式编码摘要：有损格式质量固定为 `90`，元数据策略跟随上一项公共开关；第一阶段不提供单独质量编辑控件。
- 主题设置。
- 语言设置预留。

第一阶段暂缓：

- 自动检查更新。
- 账号系统。
- 多设备同步设置。
- 企业策略配置。

## 9. 非目标

第一阶段明确不做：

- 完整图片编辑器。
- 云端压缩服务。
- 图片素材管理系统。
- 在线账号体系。
- 插件系统。
- PDF / EPS / PS 处理。
- 视频处理。
- 专业设计文件处理。
- HEIC / AVIF，除非后续验证成本可控。

## 10. 基础验收口径

第一阶段功能验收至少覆盖：

- 能打开本地单张图片并显示预览。
- 能打开本地文件夹并浏览图片列表。
- 能对单张 JPEG / PNG / WebP 执行压缩。
- 能对多张图片执行批量压缩。
- 能通过多次“添加文件”和“添加文件夹”累积来自不同位置的图片，并正确去重、排序和反馈跳过原因。
- 能将主流输入格式转换为 JPEG / PNG / WebP。
- 能区分 Alpha 通道与真实透明像素；透明图片转 JPEG 时按请求背景色确定性铺底，转 PNG / WebP 时保留透明度。
- 能按 Pixel 或百分比独立调整单张及多张图片尺寸，并符合保持比例规则。
- 能通过选框或精确 `Width / Height / X / Y` 裁剪单张图片。
- 能显示压缩或转换前后的文件大小。
- 能展示批量条目的等待、处理中、成功、失败、跳过、取消状态。
- 能选择输出目录并应用覆盖策略。
- 能保存并读取基础设置。
- 关键用户流程通过 Workflows 进入，不绕过输入、输出、能力和任务状态业务规则。
